    What it checks

    The rules cover the attacks that have actually hit open-source projects: fork pull requests running with secrets, branch names that become shell commands, and tags that were quietly moved to malicious code. Each rule has its own write-up with a broken and a fixed example.

    Run the same checks in CI

    The scanner is plain JavaScript with no dependencies to install, so the exact engine behind this page also runs as a GitHub Action and a Node CLI. Fail the build on high-severity findings, and send SARIF to the Security tab so issues show up inline on pull requests.

    From a terminal:

    npx github:yousafkhamza/pipelineguard .github/workflows --fail-on high

    Questions

    Is my workflow uploaded anywhere?

    No. Parsing and every check run in your browser. The only network request is the optional AI fix, which goes straight from your browser to Anthropic or OpenAI with your own API key. The key is kept in memory for this tab and is never stored by this site.

    What is a "pwn request"?

    Workflows triggered by pull_request_target or workflow_run run with a write token and your secrets, even when the event came from a fork. If such a workflow checks out and builds the pull request's code, anyone can open a PR that runs their code with your privileges. Rule PG001 catches this.

    Why pin actions to a commit SHA instead of @v4?

    A tag is a pointer that the action's owner, or anyone who compromises their account, can move. In March 2025 the tags of a popular action were rewritten to dump CI secrets into public logs. A full 40-character SHA can't be moved. Keep the version in a comment and let Dependabot update it.

    How is the score worked out?

    The score starts at 100. Each finding takes points off by severity (critical 35, high 20, medium 8, low 3, info 1), with smaller deductions for repeats of the same severity. Any critical finding caps the grade at D.

    Does a clean result mean the workflow is safe?

    It means none of these known patterns were found. Static checks can't see what a third-party action does internally or how your repository settings are configured. Treat PipelineGuard as a first review, not a sign-off.
